# Приёмка миграции на Greenplum

## Контракт и выпуск

1. Подтвердите состав EGP, порядок программ, привязки входов, параметры и версию Greenplum. Режим «Выпуск только для Greenplum» включает обязательную нативную сверку. Для пакета с тремя СУБД такую сверку можно отдельно сделать обязательной для Greenplum.
2. Укажите полный перечень выходных столбцов с типами и необходимыми ограничениями `NOT NULL`. Назначьте эталон каждой таблице, включая промежуточные. Включите Testifier для постоянных выходов и выберите отдельную тестовую схему.
3. Сгенерируйте и проверьте код. Для Greenplum приложение материализует типизированный выход через явный `CREATE TABLE` и первоначальный `INSERT … SELECT`. Линкер проверяет пару как один эффект создания. Последующий `INSERT`, например результат PROC APPEND, проверяется как отдельный эффект. Если контракт явно объявляет текстовые пропуски и хранение в VARCHAR без SAS-дополнения, при материализации выражений пустая строка и строка только из ASCII-пробелов становятся NULL. Непустые значения сохраняются побайтно.
4. Выполните проверку на тестовой БД. Приложение исполняет байты, которые попадут в экспорт. Один сценарий выполняется в одной сессии. На выходе сравниваются физическая схема и полные мультимножества строк с независимыми эталонами. Транзакция откатывается. При известном расхождении гейт блокируется. Если ошибка была в эталоне, зарегистрированное расхождение можно пересмотреть с обоснованием и выполнить проверку снова.
5. Утвердите проверенную ревизию. Пакет включает хеш SQL и `greenplum-validation.json` с результатами по таблицам. В пакете для нескольких СУБД эта проверка относится только к Greenplum.

Точная сверка проверяет тип, длину, точность, порядок столбцов, заданные ограничения NULL, строки и дубли. Результаты сверки хранят хеши и счётчики, без строк источника. Для набора, превышающего лимит чтения, проверка останавливается. Приёмка по независимому контролю и эквивалентность нативному SAS имеют разные основания.

## Локальный профиль

Тестовой роли нужны SELECT на входы и эталоны и CREATE только в выделенных тестовых схемах. Для локальной БД при настройке ролей учтите право CREATE в схеме `public`. Источники и эталоны должны принадлежать отдельной роли. Существующая целевая таблица блокирует прогон. Настройка соединения передаётся приложению через `--config`, пароль читается из указанной переменной окружения.

~~~json
{
  "database": {
    "target": "greenplum",
    "host": "127.0.0.1",
    "port": 55463,
    "dbname": "synthetic_lab",
    "user": "migration_validator",
    "password_env": "SAS_MIGRATION_DB_PASSWORD",
    "sslmode": "disable",
    "version_prefix": "6.27.1",
    "reference_schemas": ["oracle_lab"],
    "write_schemas": ["qa_lab"]
  }
}
~~~

`sslmode=disable` разрешён только для локального стенда. Для удалённого тестового стенда используйте `verify-full`. Greenplum 6.27.1 проверен в Docker. Версия вашего DWH и стратегия распределения данных согласуются отдельно.
